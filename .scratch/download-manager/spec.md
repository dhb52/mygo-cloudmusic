# 下载管理器与重复下载提醒

延续 `.scratch/song-download`。已实现的部分：宿主串行下载、级别探测、设置窗里显示"进行中一条 + 最近五条"。这里补两件事：**一个真正的下载管理器**（看全部正在进行与已下载）与**重复下载的提醒与拦阻**。

## 决策

1. **下载管理器是宿主自绘窗口**（与「插件管理」同类）：数据（队列、记录、文件校验）都在宿主，任何平台插件共用；入口在托盘菜单「下载…」，插件设置窗的「下载」组里也有一个「下载管理器…」（需要一个 `Services.OpenDownloads()`，与既有的 `OpenSettings()` 同型）。
2. **已下载是宿主持久化的记录**，不是目录扫描：`<userData>/downloads.json` 记 `(平台, 曲目 ref) → {名称, 级别, 路径, 大小, 时间}`。打开管理器/启动时逐条校验文件还在（不在就标「文件已不在」并提供「重新下载」/「从列表移除」）。理由：文件名是被清洗过的、无法反推身份。
3. **重复的判定与提醒**：
   - 同一首**正在下载**（排队或进行中）→ 拒绝入队，条目状态为已跳过并写「正在下载」。
   - 同一首**已下载过**（记录在且文件还在）→ 拒绝入队，写「已下载过了」。
   - 这两条同时用于**探测**：已下载或在下载中的曲目，其级别选项在弹窗里就带同样的原因（`Available:false`，宿主不进平台探测），于是用户在弹窗里就能看到、也不会点到一个注定被拒的下载。批量时聚合行因此会少算这些曲目，逐条原因解释得很清楚。
   - 原因文案不写级别：级别怎么叫是平台的事（QQ 叫「无损（FLAC）」），宿主只说"你已经有了/正在下载"；管理器里显示级别用它自己的名字（标准/极高/无损/Hi-Res）。
   - 文件还在时「重新下载」不会写第二份：宿主发现同名同大小的文件，报「已存在」并把记录放回来（正是"不要重复下载"的本意）。文件不在（记录标着「文件已不在」）时，同一个按钮才真的重新下载。要另存一份，用户自己改文件名或先移走。
4. **进行中的列表包含排队的曲目**：宿主现在只发布"正在下载的那一首"，管理器与插件设置窗都看不到排队。改为发布「正在下载 + 排队中」全部（`Phase` 都按 `running`，排队项 `Done` 为 0、`Total` 用探测到的大小），并保留 `Batch`/`Ref` 以便逐条取消。
5. **管理器窗口的内容**：
   - 顶部：下载目录 + 「更改…」/「打开」（与设置窗同一套）。
   - 「正在下载（含排队）」：名称、级别、`已下载/总量` 与百分比、`取消`；同批次的「全部取消」。
   - 「已下载」：名称、级别、大小、时间、`打开文件`、`打开目录`、`重新下载`、`从列表移除`；顶部有「清空列表」（只清记录，不删文件）。
   - 「失败与已取消」最近 5 条：原因、`重试`、`打开目录`。
   - 列表可能很长：用 `ui.List` 虚拟化，条目数与内存都不随历史增长（记录文件只留每首最近一条）。
6. **记录不随缓存淘汰**：与播放缓存互不相干；用户删了文件，记录在下一次校验时被标为「文件已不在」（不自动删，除非用户点「从列表移除」或清空）。

## 契约（SDK 增量，协议仍为 v1）

- `Services.OpenDownloads()`：即发即忘，宿主打开下载管理器窗口。
- 动作 `download-manager`。
- `plugintest.Host` 补上该方法。

## 宿主实现

- `internal/app/download_records.go`：`downloads.json` 的读写（原子写、`storage.WriteDataFile` 风格）、`lookup(platform, ref)`、`remember(item)`、`forget(platform, ref)`、`list()`；启动时加载，读时按需 `os.Stat` 校验。
- `internal/app/downloads.go`：入队前的两项拦截（在下载中 / 已下载）与探测里的同样标记；发布排队项；管理器需要的方法（取消全部、重试、清空列表、重新下载）。
- `internal/app/download_manager.go`：新窗口（复用 `plugin_manager.go` 的配色与行样式）、托盘菜单项与「下载…」入口。

## 插件实现（qqmusic）

- 设置窗「下载」组里加「下载管理器…」（`h.host.OpenDownloads()`，`DownloadAvailable` 为真才显示）。
